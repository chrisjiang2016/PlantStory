## 一、产品背景

### 1.1 市场现状

- **用户痛点**：
  - 新手养花不知从何下手，买回家就养死
  - 缺乏系统化的种植指导和养护知识
  - 植物出现问题（黄叶、病虫害）不知道如何诊断和处理
  - 市面产品功能碎片化，缺乏全流程陪伴式体验

- **市场机会**：
  - 城市居民对室内绿植、阳台园艺的需求持续增长
  - 养花已成为年轻人的新兴生活方式（小红书相关笔记超 500 万篇）
  - 现有竞品多为工具型或社区型，缺少真正的"养花管家"

### 1.2 产品愿景

**让每个人都能轻松养好一盆花，享受与植物共同成长的美好时光。**

## 二、目标用户

### 2.1 核心用户画像

#### 👤 人群 A：养花新手（占比 60%）

- **年龄**：25-35 岁
- **职业**：白领、自由职业者
- **场景**：刚开始养花，买了绿萝、多肉等入门植物，但不知道浇水频率、施肥方法
- **需求**：
  - 手把手的种植教程
  - 傻瓜式的养护提醒
  - 出问题时能快速查到解决方案

#### 👤 人群 B：进阶园艺爱好者（占比 30%）

- **年龄**：30-45 岁
- **职业**：企业中层、自由职业者
- **场景**：已有 1-2 年养花经验,家里养了十几盆植物，想系统化管理和学习进阶技巧
- **需求**：
  - 批量管理多盆植物的养护计划
  - 病虫害诊断和专业解决方案
  - 社区交流和经验分享

#### 👤 人群 C：潜在用户（占比 10%）

- **年龄**：18-24 岁学生、50+ 退休人群
- **场景**：对养花感兴趣但尚未开始，或偶尔养花但不够系统
- **需求**：低门槛的入门引导、趣味化的种植体验

## 三、产品定位与核心价值

### 3.1 产品定位

**一款为新手和进阶用户提供全流程养花陪伴的智能助手 App**

### 3.2 核心价值主张

1. **零门槛入门** — 拍照识别植物，一键获取养护方案
2. **全流程陪伴** — 从种植到养护，每一步都有清晰指引
3. **智能化提醒** — 不怕忘记浇水，系统主动推送养护任务
4. **问题排查** — 描述症状、查阅病虫害知识库并保存处理记录

### 3.3 差异化竞争优势

| 竞品特点 | 植の物语的差异化 |
|---------|-----------------|
| 功能碎片化（只有识花或只有提醒） | **全流程整合**：识别 → 种植 → 养护 → 诊断一站式解决 |
| UGC 社区为主，专业性不足 | **AI + 专业数据库**：百度 AI + Perenual API 保证内容权威性 |
| 界面冷淡、工具感强 | **日系手绘风格**：温暖、治愈的视觉体验 |
| 需要手动输入大量信息 | **引导式操作**：拍照识别 + 入园后按养护参考设置首条提醒 |

## 五、MVP 功能详细设计

> **核心闭环实现约束（2026-08-07 校正）**：识别、入园、提醒打卡必须以服务端成功响应作为状态事实。当前 V1 已支持识别、手动入园、手动创建提醒和完成重复提醒；尚未实现入园后自动生成计划、延期/跳过、系统通知调度或图片上传。完整状态流、异常恢复及后续能力准入见《[核心养护闭环与异常状态规范-V1](核心养护闭环与异常状态规范-V1.md)》。

### 5.1 核心功能：拍照识别植物

#### 功能描述
用户拍摄植物照片，系统返回植物识别结果；物种详情可用时展示养护参考，用户确认后再进入入园流程。

#### 用户流程
1. 用户点击首页"拍照识别"按钮
2. 调用相机拍照或从相册选择照片
3. 上传至百度 AI 植物识别 API
4. 返回识别结果：植物名称、置信度（服务端提供时）及可用的物种信息
5. 用户确认结果后，加载可用的植物详情与养护参考
6. 用户选择“确认并加入花园”或重新识别；识别结果不自动入园

#### 接口设计
- **百度 AI 植物识别 API**
  - 输入：图片 Base64 编码
  - 输出：植物名称、科属、置信度、百科链接
  
- **Perenual API**
  - 输入：植物名称（英文）
  - 输出：浇水频率、光照需求、适宜温度、生长周期

#### 异常处理
- 识别失败 → 提示"暂未识别出植物，请尝试拍摄更清晰的照片"
- 物种详情调用失败 → 提示“识别已保存，养护参考暂不可用”，允许稍后重试；无物种 ID 时不可直接入园

#### 验收标准
- ✅ 支持从相册选择照片，并在提交中展示可取消的加载状态。
- ✅ 识别结果明确标记为“待确认”，用户可重新识别，且不会自动入园。
- ✅ 物种详情不可用时保留已成功识别状态并提供重试。
- ✅ 识别、入园和提醒创建均以服务端成功响应作为完成事实。

### 5.3 核心功能：养护提醒

#### 功能描述
用户为植物创建并管理养护提醒（浇水、施肥、换盆等）；当前 V1 支持提醒数据管理与重复提醒续期，系统通知推送调度属于后续能力。

#### 提醒规则
| 养护任务 | 提醒频率 | 提醒文案示例 |
|---------|---------|-------------|
| 浇水 | 根据植物需求（如每 3 天） | "🌱 你的绿萝该喝水啦！" |
| 施肥 | 根据植物需求（如每 2 周） | "🌿 记得给多肉施肥哦！" |
| 修剪 | 根据植物需求（如每月） | "✂️ 月季需要修剪啦！" |

#### 用户操作
- **完成打卡** → 本次提醒标记完成；若为重复提醒，由服务端创建下一条提醒。
- **修改提醒时间** → 用户可调整下一次提醒时间
- **删除提醒** → 用户可停止该条提醒

> 延期、跳过及其审计记录尚未实现，当前 V1 不得在客户端展示为可用操作。

#### 后续技术实现（非当前 V1）
- iOS：使用 UNUserNotificationCenter（本地通知）
- Android：使用 AlarmManager + BroadcastReceiver
- 需要补齐通知权限、时区同步、离线补偿与重复投递去重后，才可承诺定时推送。

#### 验收标准
- ✅ 用户可自定义提醒时间（如每天 9:00），并成功保存到 Reminder。
- ✅ 待办列表按 `remindAt` 排序，今天、未来和已完成状态清晰区分。
- ✅ 重复提醒完成后，由服务端创建下一条提醒，并刷新列表确认。
- ✅ 支持查看多个植物的提醒；批量操作不属于当前 V1。

### 5.4 核心功能：病虫害问题排查（V1）

#### V1 能力边界
V1 提供的是**“症状记录 + 病虫害知识库查询 + 用户确认后的处理记录”**，不是自动图片诊断服务。

- 用户可描述症状，并可保存图片链接作为记录附件；当前不提供应用内图片上传、对象存储或基于图片的自动识别。
- 用户通过名称、症状关键词或类型查询病虫害知识库，查看病害说明与处理建议。
- 用户确认相关病虫害后，保存个人排查记录；历史记录仅本人可见。
- 所有治疗建议仅作日常养护参考；出现严重或持续恶化情况，应提示用户咨询园艺专业人士。

> **后续能力（非 V1 承诺）：** 接入经评估的病虫害图像模型后，才可提供“上传图片 → 候选病害 → 用户确认”的辅助识别。该能力必须展示置信度、候选项和免责声明，不能将模型结果表述为确定诊断。

#### 用户流程
1. 用户发现叶片发黄、长斑、虫害等异常。
2. 进入“病虫害问题排查”，输入症状描述；如已有图片链接，可一并保存。
3. 在知识库按关键词或类型查询可能的病虫害。
4. 查看病害说明、处理建议与预防要点，用户自行确认是否关联该知识条目。
5. 保存排查记录，后续可在个人历史中查看。

#### 常见病虫害知识库（V1 初始内容）
- 叶片发黄（缺氮、缺铁、浇水过多）
- 叶片长斑（叶斑病、炭疽病）
- 虫害（蚜虫、红蜘蛛、蚧壳虫）
- 根部腐烂（浇水过多、排水不良）

#### 知识条目示例
```
【知识条目】叶斑病
【常见诱因】通风不良、湿度过高
【处理建议】
1. 剪除病叶并妥善处理
2. 保持通风，避免叶面长期积水
3. 按产品说明谨慎使用合适的植保用品
【预防建议】
- 避免浇水时长期淋湿叶片
- 定期检查叶片状态
```

#### 验收标准
- ✅ 支持按名称关键词和类型查询病虫害知识库。
- ✅ 每个知识条目提供描述、处理建议与预防参考。
- ✅ 用户可保存含症状描述、可选图片链接和可选知识条目的排查记录。
- ✅ 用户仅能查看自己的排查历史与详情。
- ✅ 页面和接口不得声称已提供自动病虫害 AI 识别或应用内图片上传。

### 5.5 辅助功能：植物百科

#### 功能描述
提供常见植物的养护指南,按场景和难度分类,方便用户查阅。

#### 分类逻辑
- **按场景**：室内 / 阳台 / 办公室 / 室外
- **按难度**：新手友好 / 进阶挑战 / 专家级
- **按类型**：观叶植物 / 多肉植物 / 开花植物 / 水培植物

#### 内容结构
每个植物条目包含：
- 基本信息（学名、科属、原产地）
- 养护要点（浇水、光照、温度、施肥）
- 常见问题 FAQ
- 繁殖方法

#### 验收标准
- ✅ V1.0 覆盖 50 种常见植物
- ✅ 支持按场景/难度筛选
- ✅ 支持关键词搜索
- ✅ 内容可离线查看（本地缓存）

## 六、非功能性需求

### 6.1 性能要求
- **启动速度**：冷启动 ≤ 3 秒
- **页面加载**：普通页面 ≤ 1 秒，图片密集页面 ≤ 2 秒
- **API 响应**：识别类接口 ≤ 3 秒，查询类接口 ≤ 1 秒

### 6.2 稳定性要求
- **Crash 率**：≤ 0.5%
- **API 可用性**：≥ 99.5%
- **数据一致性**：用户数据实时同步（云端 + 本地双重备份）

### 6.3 兼容性要求
- **iOS**：iOS 14.0+
- **Android**：Android 8.0+（API Level 26+）
- **屏幕适配**：支持主流分辨率（375×667 ~ 414×896）

### 6.4 安全性要求
- **API 密钥**：存储在服务端，客户端不可见
- **用户数据**：云端加密存储（AES-256）
- **隐私合规**：遵循 GDPR 和《个人信息保护法》

## 七、技术方案概要

### 7.1 技术栈
- **前端**：React Native（跨平台）
- **后端**：Node.js + Express
- **数据库**：MongoDB（用户数据） + Redis（缓存）
- **云服务**：阿里云 OSS（图片存储） + CDN（加速）
- **推送服务**：极光推送（JPush）

### 7.2 第三方服务
| 服务 | 用途 | 成本 |
|------|------|------|
| 百度 AI 植物识别 | 拍照识别植物 | 免费额度 500 次/天，超出 ¥0.002/次 |
| Perenual API | 植物数据库 | 免费额度 300 次/天，付费 $19/月 |
| 极光推送 | 养护提醒推送 | 免费额度 1000 万次/月 |
| 阿里云 OSS | 图片存储 | ¥0.12/GB/月 |

### 7.3 数据流架构
```
[客户端] 
   ↓ 上传照片
[CDN] → [后端 API] 
             ↓ 调用
        [百度 AI / Perenual API]
             ↓ 返回数据
        [MongoDB 存储]
             ↓ 推送
        [极光推送] → [客户端通知]
```

## 十、风险与应对

### 10.1 技术风险

| 风险 | 影响 | 应对措施 |
|------|------|---------|
| 第三方 API 不稳定 | 识别失败率上升 | 本地缓存常见植物数据 + 多 API 源备份 |
| 识别准确率不达标 | 用户体验差 | 引入人工复核机制 + 持续优化模型 |
| 推送送达率低 | 用户错过养护时间 | 多渠道推送（通知 + 短信 + 邮件） |

### 10.2 业务风险

| 风险 | 影响 | 应对措施 |
|------|------|---------|
| 用户留存率低 | 无法形成用户习惯 | 强化游戏化设计 + 每日签到奖励 |
| 竞品抄袭 | 市场份额被瓜分 | 快速迭代 + 打造品牌差异化 |
| 商业化路径不清晰 | 无法盈利 | V1.0 专注用户增长，V2.0 再启动变现 |

### 10.3 合规风险

| 风险 | 影响 | 应对措施 |
|------|------|---------|
| 隐私数据泄露 | 法律风险 + 信任危机 | 数据加密 + 定期安全审计 |
| 应用商店审核被拒 | 上线延期 | 提前熟悉应用商店规则 + 准备申诉材料 |
