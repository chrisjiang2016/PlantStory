## 一、问题背景

### Vercel 部署失败（初始状态）

**问题现象：**
- GitHub Actions workflow 成功构建了 Flutter Web（`client/build/web`）
- 但 Vercel 部署失败，报错：`Error: Command "flutter build web --release" exited with 127`
- Vercel 日志显示：`bash: flutter: command not found`

**根本原因：**
- Vercel 构建环境中没有安装 Flutter SDK
- 但 workflow 设计意图是"GitHub Actions 构建 → Vercel 只负责复制文件"
- 实际提交中 `client/build/web/` 目录被 `.gitignore` 规则阻止了提交

**影响：**
- Vercel 部署失败，生产 Demo 无法访问
- 用户无法通过公网体验 Flutter Web 应用

### 启动页卡死问题（第二阶段）

**问题现象：**
- 修复 Vercel 部署后，访问 Demo URL 页面卡在"正在恢复登录状态..."
- 转圈动画一直显示，无法进入登录页或花园页

**根本原因：**
1. **前端超时缺失**：
   - `SplashPage` 和 `AuthenticatedShell` 调用 `restoreSession()` 时没有硬超时
   - Web 端遇到 CORS 预检被拦或后端冷启动时，Dio 的 `connectTimeout`/`receiveTimeout` 不一定生效
   - `AsyncValue` 停留在 loading 状态，页面永久显示转圈动画

2. **后端 CORS 限制**：
   - 后端 CORS 配置写死了特定的 Vercel 预览域名：
     ```typescript
     /^https:\/\/plant-story-[a-z0-9-]+-jly2008s-projects\.vercel\.app$/
     ```
   - Vercel 每次部署会生成新的域名（例如 `plant-story-xxxxx.vercel.app`）
   - 新域名的 `/auth/web/refresh` 请求被 CORS 拦截

**影响：**
- 用户访问 Demo 后无法进入应用
- 演示体验完全中断

### 修复 2：解决启动页卡死问题

#### 前端：添加恢复登录态的硬超时

**修改文件：** `plant-story/client/lib/src/app.dart`

**SplashPage 超时保护：**

```dart
// 恢复登录态最多等待 8 秒。
// Web 端遇到 CORS 预检被拦、后端冷启动或网络挂起时，Dio 的超时不一定生效，
// 这里用硬超时兜底，避免启动页永久停在"正在恢复登录状态"。
try {
  await ref
      .read(authControllerProvider.notifier)
      .restoreSession()
      .timeout(const Duration(seconds: 8));
} catch (_) {
  // 超时或异常都按未登录处理，交给登录页兜底。
}
if (!mounted) return;
final user = ref.read(authControllerProvider).valueOrNull;
context.go(user == null ? '/login' : '/garden');
```

**AuthenticatedShell 超时保护：**

```dart
final currentUser = ref.read(authControllerProvider).valueOrNull;
if (currentUser == null) {
  // 与 SplashPage 相同的兜底：恢复登录态最多等待 8 秒，超时按未登录处理。
  try {
    await ref
        .read(authControllerProvider.notifier)
        .restoreSession()
        .timeout(const Duration(seconds: 8));
  } catch (_) {
    // 忽略，交给下面的未登录分支跳转登录页。
  }
}
```

**设计理由：**
- Dio 的 `connectTimeout` 和 `receiveTimeout` 在 Web 平台遇到 CORS 预检失败时可能不会触发
- 添加应用层的 8 秒硬超时，确保用户不会永久停留在加载页
- 超时后按未登录处理，让用户可以正常进入登录页

#### 后端：放开 Vercel 域名的 CORS 限制

**修改文件：** `plant-story/backend/src/main.ts`

```diff
   // ── CORS（允许本地开发及已发布的 Web Demo，并支持 HttpOnly refresh cookie）──
+  // Vercel 每次部署会生成不同的预览域名，这里放开 *.vercel.app 下 plant-story 前缀的所有域名，
+  // 避免换域名后 Web 端 refresh 请求被 CORS 拦截、启动页卡在"正在恢复登录状态"。
   app.enableCors({
     origin: [
       /^http:\/\/localhost:\d+$/,
       /^http:\/\/127\.0\.0\.1:\d+$/,
       'https://chrisjiang2016.github.io',
-      /^https:\/\/plant-story-[a-z0-9-]+-jly2008s-projects\.vercel\.app$/,
+      /^https:\/\/plant-story[a-z0-9-]*\.vercel\.app$/,
     ],
     credentials: true,
   });
```

**正则规则说明：**
- 原规则：`/^https:\/\/plant-story-[a-z0-9-]+-jly2008s-projects\.vercel\.app$/`
  - 只允许特定格式的旧预览域名
- 新规则：`/^https:\/\/plant-story[a-z0-9-]*\.vercel\.app$/`
  - 允许所有 `plant-story*.vercel.app` 域名（包括 production 和 preview）
  - 覆盖 Vercel 自动生成的所有部署域名

**部署要求：**
- 后端代码修改需要在 Railway 重新部署才能生效
- 如果 Railway 连接的是 GitHub `main` 分支，推送后会自动触发部署
- 如果不是自动部署，需要在 Railway 控制台手动 Redeploy

## 四、技术决策记录

### 决策 1：提交 Flutter Web 构建产物到 Git

**背景：**
- Vercel 构建环境没有 Flutter SDK
- 在 Vercel 上安装 Flutter 会增加部署时间和复杂度
- GitHub Actions 已经可以成功构建 Flutter Web

**方案：**
- 允许 `client/build/web/` 被 Git 跟踪
- 每次需要部署时，在本地或 CI 中构建 Flutter Web，然后提交产物
- Vercel 只需要复制静态文件，不需要安装 Flutter

**优点：**
- ✅ 部署速度快（Vercel 只需复制文件）
- ✅ 部署稳定（不会因为 Flutter 版本问题失败）
- ✅ Vercel 不需要安装 Flutter SDK（节省时间）

**缺点：**
- ❌ 仓库体积增加约 3MB（每次构建都会变化）
- ❌ 违反"不提交构建产物"的最佳实践
- ❌ 如果忘记重新构建，部署的代码可能与源码不一致

**未来优化方向（可选）：**
1. 使用 Vercel Build Cache
2. 在 Vercel 上配置 Flutter SDK（需要自定义构建镜像）
3. 使用专门的 Flutter 部署平台（如 Firebase Hosting）

**当前决策：** 保持现有方案（提交构建产物），优先保证部署稳定和速度。

### 决策 2：应用层超时兜底

**背景：**
- Dio 的 `connectTimeout` 和 `receiveTimeout` 在 Web 平台不可靠
- CORS 预检失败时，底层 HTTP 请求可能不会正确触发超时
- `AsyncValue.loading` 会一直保持，导致 UI 永久显示加载动画

**方案：**
- 在 `restoreSession()` 调用外层添加 Dart 的 `.timeout(Duration(seconds: 8))`
- 超时后捕获异常，按未登录处理，让用户进入登录页
- 8 秒是一个合理的等待时间：既给网络请求足够的时间，又不会让用户等太久

**替代方案（未采用）：**
1. ❌ 依赖 Dio 超时配置 — 在 Web CORS 场景下不可靠
2. ❌ 修改 `restoreSession()` 内部逻辑 — 侵入性强，影响所有调用方
3. ❌ 在 UI 层添加重试按钮 — 增加用户操作成本

**当前决策：** 应用层超时兜底，在调用侧添加 `.timeout()`，影响范围小且有效。

### 决策 3：放开 Vercel 所有 plant-story 域名的 CORS

**背景：**
- Vercel 每次部署会生成新的预览域名
- 原 CORS 正则写死了特定格式的域名
- 新域名的请求会被 CORS 拦截

**方案：**
- 将正则改为 `/^https:\/\/plant-story[a-z0-9-]*\.vercel\.app$/`
- 允许所有 `plant-story*.vercel.app` 子域名
- 包括 production、preview 和旧的部署域名

**安全考虑：**
- ✅ 仍然限制在 `*.vercel.app` 域名下
- ✅ 仍然限制 `plant-story` 前缀
- ✅ 只允许 HTTPS 连接
- ⚠️ 任何人都可以在 Vercel 上创建 `plant-story*` 项目并访问我们的 API
  - 但需要知道 Railway 后端 URL
  - 且需要通过正常的认证流程
  - 风险可控

**替代方案（未采用）：**
1. ❌ 每次部署后手动更新 CORS 配置 — 运维成本高
2. ❌ 使用 Vercel 的自定义域名并写死 — 需要购买域名
3. ❌ 在后端读取动态 CORS 配置 — 增加复杂度

**当前决策：** 放开 `plant-story*.vercel.app` 所有域名，优先保证部署流畅。

## 九、经验教训

### 教训 1：构建产物与 CI/CD 的权衡

**问题：** 最初没有意识到 `.gitignore` 规则会阻止 `client/build/web/` 提交。

**经验：** 在设计 CI/CD 流程时，需要明确：
- 谁负责构建（本地、CI、部署平台）
- 构建产物是否需要提交到 Git
- 如果不提交，部署平台如何获取构建产物

**未来优化：** 使用 CI 自动构建并提交，或者在 Vercel 上直接构建（需要配置 Flutter SDK）。

### 教训 2：Web 平台的超时机制不可靠

**问题：** 以为 Dio 的 `connectTimeout` 和 `receiveTimeout` 在所有平台都会生效。

**经验：** 在 Web 平台上：
- CORS 预检失败不会触发正常的 HTTP 超时
- `fetch` API 的 timeout 行为与原生平台不同
- 需要在应用层添加额外的超时保护

**未来优化：** 所有关键的异步操作都应该有应用层超时兜底，而不是只依赖底层库。

### 教训 3：动态域名与 CORS 配置

**问题：** Vercel 预览域名每次都不同，导致 CORS 配置需要频繁更新。

**经验：** 对于动态域名：
- 可以用正则匹配一类域名（如 `*.vercel.app`）
- 或者使用固定的自定义域名
- 需要在安全性和便利性之间权衡
